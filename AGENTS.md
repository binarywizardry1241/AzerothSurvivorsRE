Reuse a suitable existing checkout; create a worktree when isolation is useful. Do not create unrelated clones or project folders.
- Keep all project source, documentation, plans, notes, scripts, logs, downloads, generated artifacts and temporary files inside the primary checkout or a registered linked worktree. Do not put project material in external documentation directories, shared temporary folders or other repositories.
- Run project commands from the checkout that owns the work, or a directory beneath it. Coordinate access to shared files, Git state and runtime resources across worktrees. Worktree permission does not authorize searching unrelated folders.

Keep every analysis output, Ghidra database, extract, log and temporary file inside an authorized project workspace; do not modify the installed game, saves or configuration.
- Existing installed tools and their authentication may be used. Reuse compatible tool/dependency installations where supported instead of duplicating them in every worktree; keep machine-specific configuration local and ignored.
- These rules also apply to any delegated agents.

## Builds, validation and disk usage

Complete as much source implementation as possible for the given task, within its scope and the recovered evidence, before requesting a build. ## Reconstruction fidelity — hard rule

- Work scope: **playable zone integration using the recovered mechanics and real MPQ world**. Continue EXE-bound REA recovery for missing connections; distinguish initial integration from verified native parity. All validation remains subject to the builds and compilation rule above.

- **Full co-op reconstruction is in scope, including client, networking and server source.** Recover and implement the complete EXE-bound cooperative behavior: discovery/directory and relay services, hosting/joining, session routing and transport, world bootstrap/synchronization/replication, in-run party mechanics, server party lifecycle and cooperative UI/addon/localization consumers. Follow necessary dependencies beyond the four named AS modules; do not limit reconstruction to presentation or stop a recovery branch because it contains co-op, networking or server logic. Reuse the existing benilla/wenilla engine and preserve the EXE-fidelity rules.
- **Do not run a co-op server.** Do not start, host, deploy or operate a game server, relay or lobby/directory service, including a local or loopback host session. Complete source reconstruction and permitted static/non-compiling checks without requiring a running server. Compilation and client/game/network execution retain their separate authorization rules above; lifting co-op source restrictions does not authorize those actions. Partial source correspondence, complete implementation, compilation, execution and original/rebuilt parity remain distinct evidence levels.

- The **installed, hash-verified EXE is the authoritative specification** for the rebuilt source code. Discover its actual version/hash through `python3 -B scripts/register-target.py --inspect-installed`; resolve coverage through `docs/analysis/coverage/targets.json` and `scripts/coverage_common.py`. The registered baseline is **0.139.1**, bound by `docs/analysis/target-refresh-0.139.1.json`; `docs/CURRENT-STATE.md` records discovery/recovery limits or any newer installed identity awaiting refresh. Detect new versions or changed same-version bytes before using coverage; reject stale accounting and never silently fall back to an older inventory. Match the installed target's actual appearance, behavior, defaults, restrictions, state transitions, data formats and file operations exactly within the active scope.
- Reconstruct from the EXE using REA/Ghidra, hash-bound code/data evidence and controlled runtime comparisons. Verify reused benilla or conventional WoW behavior against this target before treating it as the implementation specification.
- Prioritize REA-driven source reconstruction and the existing public benilla/wenilla engine source. Validate the reconstructed level path locally; controlled original/rebuilt comparisons remain separate evidence and must be recorded when actually performed.
- Do not invent or substitute behavior to fill a recovery gap. Treat existing provisional code and every observed difference as incomplete reconstruction until recovered behavior replaces it and the rebuilt application is checked against the EXE.
- Keep claims traceable to the selected target and the owning evidence/report. Distinguish recovered data, implemented code and verified parity. A successful build, matching screenshot, available label or vendored source alone does not establish functional parity.
- Gameplay fidelity baseline: **movement, camera and the underlying interface must follow the target's Vanilla WoW 1.12.1 client behavior**. Reuse the existing benilla/wenilla player controller, mouse/orbit/follow/zoom behavior and real FrameXML/Lua interface with action bars and unit frames; verify target-specific changes against the supplied EXE. Fixed screen-relative movement, a fixed camera and replacement Bevy HUD widgets are temporary deviations, not an acceptable reconstruction baseline. **Level-up upgrade choices and treasure/reward screens must also match the EXE's actual presentation and interaction**, including its custom overlay layer; recovered choice rules alone do not establish UI fidelity. Do not fill these gaps with an invented substitute.
- The active goal is **loadable, playable levels wired to the mechanics already recovered**, including exact menu and gameplay presentation. **Complete the five reconstruction scopes: selected-target coverage, treasure, run effects/progression, upgrades and menu fidelity.** REA/Ghidra recovery, implementation, tests and isolated original/rebuilt comparisons are resumed for these scopes, subject to the builds and compilation rule above. **Use focused commits in an authorized checkout. Push completed `$fixgap` repairs to the configured public GitHub repository's `main`; other work remains local unless the user explicitly authorizes delivery. Do not open PRs.** Preserve existing work and keep QA saves/configuration inside the active project workspace.

## Commit discipline

- Each commit must have one clear purpose: a cohesive fix, feature, addition, refactor, or documentation change. Include the directly related code, tests, and documentation together; separate unrelated changes even when they touch the same file or were completed in the same session.
- Split large or mixed pending work into a series of focused commits, in dependency order. This applies to changes already in progress as well as future work; carry the split through before completing the work, rather than leaving it as optional cleanup. Do not bundle accumulated work into a giant catch-all commit, such as 20,000 lines spanning multiple changes.
- Review the full pending diff to identify the logical changes, then stage explicit files or hunks for each commit and inspect the staged diff before committing. Do not sweep unrelated work into a commit with blanket staging.
- Keep each commit coherent and independently reviewable. Split by purpose rather than mechanically by file or line count; explain why an unusually large cohesive change cannot reasonably be split further. Use the commit message to describe the specific fix, change, or addition.
- Apply this discipline throughout the work and at the end of the session. Do not rewrite existing commits or published history merely to apply it without the user's explicit authorization.
