# Menu character preview

Reviewed and implementation started: **2026-10-16**. Target: **0.92.0** main menu; gameplay is outside this task. This report describes the owned preview module, not proof of original-menu parity.

## Integration

[`preview.rs`](../../crates/azeroth-survivors-re/src/preview.rs) provides `HeroPreviewPlugin`, an input resource `HeroPreview` and output resource `HeroPreviewOutput`. `HeroLook` contains race, sex, class and the five appearance values; `yaw` is in radians. The output image is a transparent offscreen target populated after Startup. Its initial124×168 size matches the recovered picker portrait; `menu::sync_preview` measures the marked ImageNode's computed physical size and transform and resizes the target, capped at2048 pixels per dimension as in the native request. The menu displays that handle and updates race/appearance/equipment input when selection changes. Native default facing is0.35 radians.

`HeroPreview.equipment` is an array of ten optional `HeroGearItem { display_id, inv_type }` entries in Armory's internal slot order. None preserves the native0.92 baseline for that slot; display_id0 removes it while preserving separate starting-shirt clothing; a real display replaces its starting item. These entries feed body compositing, armor geosets, helmet visibility and rigid equipment models. Selection synchronization is owned by the menu/Armory integration. The picker portrait accepts the parent's drag-to-turn input.

The launcher requires Bevy's explicit `3d_bevy_render` feature. It keeps its own App and does not start benilla's stock login, networking, world, terrain or gameplay systems. Building the source requires neither the reference EXE nor MPQs. Runtime models and textures come from the configured `--data-dir` / `WOW_DATA` MPQ chain; missing data produces an explicit preview status and no substitute character. `preview::check_assets()` validates the 40 native picker class/race pairs and both sexes (80 looks) without opening a window, including geometry/skin weights, Stand, composites, sockets and every referenced item texture. `HeroPreview.tabard` adds the progression system's native look lane18 without changing the ten-slot equipment adapter.

## Actual asset path

1. `CharCreateCatalog::body_display(race, sex)` resolves `ChrRaces.dbc`'s male/female display id; `load_creature_catalog` resolves that id through `CreatureDisplayInfo.dbc` and `CreatureModelData.dbc` to the selected body's M2 and display scale.
2. `CharacterGeosets::visible_geosets` filters body/hair/facial-hair/armor geometry using `CharHairGeosets.dbc`, `CharacterFacialHairStyles.dbc`, `HelmetGeosetVisData.dbc` and the current appearance/equipment selectors.
3. `CharSections::composite_body` composes skin, face, hair/scalp, facial hair, underwear and the worn armor regions. The hair sheet and tauren extra-skin sheet bind separately to the M2's runtime texture slots.
4. The recovered0.92 native starting tables supply item/display ids for `(race, class)`, independently of sex. `ArmoryCatalog::starter` exposes the66 item records and72 race/class19-slot tables recovered from `0x1453df460`/`0x1453df730`. For Human Warrior the baseline is sword25/display1542, shirt38/display9891, pants39/display9892, boots40/display10141 and shield2362/display18730. The menu supplies saved equipped/cosmetic overrides through the corrected native19-slot-to-internal-slot adapter. A two-handed primary clears the offhand, matching native `0x1453dfcf0`. `ItemDisplayInfo.dbc` supplies body-region textures and item model/texture names. Real helm, shoulders and drawn items attach to authored body M2 sockets; native dressup keeps ranged weapons in hand.
5. `parse_m2_skeleton`, `parse_m2_animations` and `parse_m2_attachments` provide the body skeleton, Stand animation and rider sockets. The module evaluates weighted body positions/normals on the CPU and moves rigid gear with its attachment bone. It reads the authored global-sequence bone channels (including eyelid loops) and overlays the HandsClosed finger pose on weapon-holding hands using the existing engine's weight-8 convention. The WoW→Bevy coordinate conversion is the existing engine convention `(-y, z, -x)`.

6. The binary's missing `HeroPreviewPlugin` is bound through its vtable to `0x1406a9400`, then its registered system wrapper `0x140730500` and bridge `0x1406c97f0`. The bridge uses the engine's `dressup` model pane. Its request writer `0x1406636b0` and picker caller `0x140044c40` establish the facing and physical-size seam. The existing DressUp framing route selects authored M2 camera1; the owned renderer now evaluates that camera's eye, target, roll, clip planes and diagonal-to-vertical FOV conversion instead of fitting a generic studio camera to bounds. The fallback follows the existing engine's WoW character-camera convention. Static path bindings and REA evidence IDs are curated in [canvas-preview-native-paths.json](https://github.com/binarywizardry1241/AzerothSurvivorsRE/blob/869aa7fbc7a177d6dacaa1b3e69b12b24842cc47/docs/analysis/evidence/0.92/canvas-preview-native-paths.json).

The source owners are [`characters/`](../../crates/benilla-formats/src/characters/), [`creatures.rs`](../../crates/benilla-formats/src/creatures.rs), [`items.rs`](../../crates/benilla-formats/src/items.rs) and [`models/`](../../crates/benilla-formats/src/models/).

## Why a new menu module

There is no `HeroPreviewPlugin` in the vendored benilla source. Its full character renderer is private `benilla-app` code: [`entities/attach/preview.rs`](../../crates/benilla-app/src/entities/attach/preview.rs) assembles the appearance and equipment, while [`portrait/glue_booth.rs`](../../crates/benilla-app/src/portrait/glue_booth.rs) renders its live booth. Their public launcher seam `run_with` receives the already built client, including private stock login/game plugins. It is not a menu-only constructor.

The owned implementation uses the already public data/format layer and leaves that unrelated client stack inactive. It creates actual selected-race geometry and composed art, rather than a placeholder model.

## Native material and gamma integration

The supplied0.92 EXE contains the vendored `wow_model.wgsl`, `ui_gamma.wgsl`, `ui_node_gamma.wgsl` and `ui_slice_gamma.wgsl` **byte-for-byte after newline normalization only** (Windows CRLF in the EXE). [menu-native-shader-bindings.json](https://github.com/binarywizardry1241/AzerothSurvivorsRE/blob/869aa7fbc7a177d6dacaa1b3e69b12b24842cc47/docs/analysis/evidence/0.92/menu-native-shader-bindings.json) records source/native digests, lengths and original file offsets. The native type inventory also contains `benilla_app::ui_gamma::UiGammaPlugin` and `UiGammaLane`. Source presence alone does not prove every shader permutation, but the material/gamma behavior is now based on shipped shader text.

`preview.rs` now registers the public `WowModelMaterial` material plugin and shader sources from `benilla-assets`. The material builder from `benilla-world::model_render` supplies the authored alpha-test/additive/multiply blends, depth flags and environment-map marker. The character-pane light is the existing `ModelLight::character` folded into a public `LightBlob` SH probe as `TileScene::blob` does; provisional PBR directional lamps have been removed. This uses the libraries without adding their world, client, login, physics, network or gameplay plugins. The extra library dependency still compiles its dependency graph, including Avian; that is build cost, not an active gameplay integration.

The owned `menu_gamma.rs` adapts the engine's isolated UI-gamma node and references its three original WGSL files with `include_str!`, so shader knowledge is not duplicated. Bevy UI composites in the shipped gamma lane, followed by its final decode. The model camera decodes its raw-gamma float target once before Bevy ImageNode samples it; the UI node restores that gamma value for the shared final composition. Per-view uniform buffers keep preview identity decoding separate from the menu's display-gamma ramp. The menu reads the existing Options gamma CVar and keeps the engine's0.25–4 consumer clamp. Build9 and build11 rendered the integrated graph with the picker and actual character visible and no reported WGSL error; exact native material/lighting appearance remains under comparison.

## Remaining parity limits

- The recovered dressup/M2 camera and engine material/character-light paths are implemented and rendered in build9/build11. Exact lighting/gamma appearance, camera-scale overrides and scene background remain under native comparison.
- Native starting outfits and resolved Armory display overrides are implemented; the native-baseline asset check passed all80 default looks, and integrated captures render starter gear. All saved cosmetic combinations and exact native/rebuilt visual comparison remain incomplete. Earlier DBC-only outfit captures are historical.
- The current animation path selects Stand and implements weighted bones, global-sequence channels, weapon-hand grip and rigid equipment. Native variation scheduling, camera-facing eye/glow geometry, parent-inheritance flags and per-item animation/effects require further integration or evidence. Global-sequence channels currently interpolate the exported key arrays; original track interpolation modes have not been independently verified for every model.
- The public material now supplies multiply/2× multiply, authored depth flags and environment maps. Dynamic material animation, per-item effects and all billboard behavior are still incomplete. No claim of a visual match for all equipment/appearances follows from the shared shader alone.
- The target now follows the portrait's physical computed size with the native2048 cap. Exact original antialiasing and full GPU render behavior remain unverified.
- This module renders the selected appearance/equipment; separate menu modules own saves, progression, Armory and Talents behavior. Run entry and gameplay are outside this module and the current milestone.

## Validation

The parent's integrated build and first visual capture succeeded: an actual selected Human model and idle pose rendered in the picker. The first headless `--check-preview` run resolved76/80 native default looks; four Tauren female combinations attempted an unused missing hair sheet. The source now follows the engine binder's visible-batch guard, avoiding auxiliary skin loads when no visible batch uses that slot. The parent's fresh native-baseline `--check-preview` passed all80 race/sex/class looks. Integrated build7/capture also rendered the M2-camera route, native starter gear, physical portrait target size, recovered canvas scaling, class atlas and boss chips. Subsequent build9/build11 captures rendered the actual-material/SH-light/gamma graph successfully; full cosmetic/tabard combinations are not covered by the default-look asset check. Record actual subsequent results in [CURRENT-STATE](../CURRENT-STATE.md) and [verification-needed](../verification-needed.md) and the main [menu validation report](menu-validation.md); an implemented path alone is not runtime proof.

Build9 integrated the public WowModelMaterial/light route and gamma decode successfully: the picker and actual model rendered after the main/background UI roots received explicit z-order and the window camera was marked IsDefaultUiCamera. No WGSL runtime error was reported. The new material appearance is under native capture comparison; this is not a visual-parity assertion. The additional native gradient-stop color bridge is documented in [main-menu-native-layout.md](main-menu-native-layout.md).
